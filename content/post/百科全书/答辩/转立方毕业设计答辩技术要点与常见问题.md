本文整理毕业设计项目 **“转立方”校园二手交易平台** 的答辩版技术说明，适合用于毕业论文答辩、PPT 讲稿准备和评委问答复盘。

项目整体采用 **微信原生小程序 + Spring Boot 后端 + MySQL + Redis + MyBatis-Plus + Spring Security + JWT** 的技术架构，实现了用户登录、商品发布、学生认证、商品收藏、订单交易、即时聊天、举报处理、后台管理等功能。

<!--more-->

## 一、项目一句话介绍

“转立方”是一个面向校园场景的二手交易平台，用户可以通过微信小程序登录系统，完成学生认证后发布二手商品，并通过聊天、收藏、下单、举报和后台审核等功能完成校园二手交易闭环。

答辩时可以这样说：

> 我的毕业设计是一个校园二手交易微信小程序，前端采用微信原生小程序开发，后端采用 Spring Boot 构建 REST API，数据库使用 MySQL，Redis 用于邮箱验证码等临时数据缓存，系统通过 Spring Security + JWT 实现无状态登录鉴权，并结合学生认证、商品管理、聊天消息和后台审核实现完整的校园交易流程。

## 三、系统总体架构

系统整体可以分为三层：

1. **表现层**：微信小程序页面，负责用户交互、页面展示、表单提交和接口请求。
2. **业务层**：Spring Boot 后端，负责登录鉴权、商品管理、订单处理、聊天消息、后台审核等核心业务逻辑。
3. **数据层**：MySQL 和 Redis，MySQL 负责持久化业务数据，Redis 负责验证码等临时数据。

答辩时可以这样讲：

> 系统采用前后端分离架构，小程序端只负责界面展示和用户交互，所有业务规则都放在后端实现。后端通过 REST API 向前端提供服务，数据库层使用 MySQL 持久化核心业务数据，Redis 存储验证码这类短生命周期数据。这样的设计可以降低前后端耦合度，也便于后期扩展管理后台、移动端或 Web 端。

## 四、微信原生登录实现

### 4.1 登录流程

微信登录的核心流程如下：

1. 用户在小程序端点击微信登录。
2. 小程序调用 `wx.login()` 获取临时登录凭证 `code`。
3. 前端把 `code` 发送给后端登录接口。
4. 后端携带 `appid`、`secret`、`code` 调用微信接口 `jscode2session`。
5. 微信服务器返回用户的 `openid`。
6. 后端根据 `openid` 查询用户是否存在。
7. 如果用户不存在，则自动注册新用户。
8. 如果用户存在，则更新登录时间等信息。
9. 后端生成 JWT token 返回给小程序。
10. 小程序将 token 存入本地缓存，后续请求携带 token。

### 4.2 前端关键实现

关键位置：

- `webFront/pages/auth/login/login.js`

核心函数：

- `onWeChatLogin()`

主要逻辑：

```js
wx.login({
  success: (res) => {
    // res.code 发送给后端
  }
})
```

前端拿到后端返回的 token 后，通过：

```js
wx.setStorageSync('token', data.token)
```

保存登录状态。

### 4.3 后端关键实现

关键位置：

- `backEnd/src/main/java/com/example/backend/controller/AuthController.java`
- `backEnd/src/main/java/com/example/backend/service/impl/WeChatAuthServiceImpl.java`

核心方法：

- `AuthController.login(LoginDTO dto)`
- `WeChatAuthServiceImpl.getOpenid(String code)`

后端调用微信接口：

```text
https://api.weixin.qq.com/sns/jscode2session
```

请求参数主要包括：

- `appid`
- `secret`
- `js_code`
- `grant_type=authorization_code`

### 4.4 答辩讲解口径

答辩时可以这样说：

> 微信小程序登录不是直接把微信账号密码给后端，而是小程序先调用 `wx.login()` 获取一次性的 `code`。后端再拿这个 `code` 加上小程序的 `appid` 和 `secret` 请求微信官方接口，换取用户唯一标识 `openid`。系统用 `openid` 作为微信用户身份标识，如果数据库中不存在该用户就自动注册，如果存在就直接登录，最后由后端签发 JWT token 给前端。

## 五、JWT 鉴权实现

### 5.1 当前项目的真实实现

需要特别注意：当前项目实现的是 **单 JWT token 鉴权**，不是完整的 **access token + refresh token 双 token 机制**。

当前项目中：

- 有普通用户 token。
- 有管理员 token。
- 普通用户 token 和管理员 token 分开生成。
- 没有 refresh token。
- 没有 token 刷新接口。
- 没有 access token 与 refresh token 的双过期时间设计。

因此答辩时建议准确表述为：

> 系统采用 Spring Security + JWT 实现无状态单令牌鉴权，并对普通用户和管理员分别签发不同类型的 token。

不要说成：

> 系统已经实现 JWT 双 token 鉴权。

除非后续代码真的补上 refresh token 机制。

### 5.2 JWT 生成逻辑

关键位置：

- `backEnd/src/main/java/com/example/backend/util/JwtUtil.java`

核心方法：

- `generate(Long userId, String openid)`
- `generateAdmin(Long adminId)`
- `parse(String token)`
- `validate(String token)`
- `getUserId(String token)`
- `getAdminId(String token)`

普通用户 token 中主要包含：

- 用户 ID
- openid
- 过期时间
- 签名信息

管理员 token 中主要包含：

- 管理员 ID
- 管理员身份标识
- 过期时间
- 签名信息

### 5.3 JWT 校验流程

关键位置：

- `backEnd/src/main/java/com/example/backend/config/JwtAuthFilter.java`
- `backEnd/src/main/java/com/example/backend/config/SecurityConfig.java`

请求鉴权流程：

1. 前端请求接口时，在请求头中携带：

```text
Authorization: Bearer <token>
```

2. 后端 `JwtAuthFilter` 拦截请求。
3. 从请求头中解析 token。
4. 调用 `JwtUtil.validate(token)` 校验签名和过期时间。
5. 校验通过后，解析用户 ID 或管理员 ID。
6. 将身份信息放入 `SecurityContextHolder`。
7. 后续 Controller 通过当前登录用户信息执行具体业务。

### 5.4 为什么使用 JWT

使用 JWT 的原因：

1. **无状态**：服务端不需要保存 Session，适合前后端分离。
2. **扩展性好**：后端多实例部署时，不需要共享 Session。
3. **接口调用方便**：前端只要在请求头携带 token 即可。
4. **适合小程序场景**：小程序没有传统浏览器 Session 机制，token 鉴权更自然。

### 5.5 token 过期处理

前端统一请求工具会处理接口返回的未登录或无权限状态：

- 普通用户 token 失效后，清理本地 `token` 和 `userInfo`。
- 管理员 token 失效后，清理本地 `adminToken` 和 `adminInfo`。
- 然后提示用户重新登录。

关键位置：

- `webFront/utils/request.js`

## 六、如果老师问“双 token”，应该怎么回答

如果老师问：

> 你的系统有没有实现 JWT 双 token？

建议回答：

> 当前系统实际实现的是单 JWT token 鉴权，普通用户和管理员分别签发 token，但还没有实现 access token 和 refresh token 的双 token 机制。因为本系统是毕业设计项目，用户规模和安全需求相对可控，所以目前采用 7 天有效期的单 token 方案来降低复杂度。后续如果上线到真实生产环境，可以扩展为双 token：access token 设置较短有效期，refresh token 设置较长有效期并存入 Redis 或数据库，通过刷新接口换取新的 access token，同时支持 refresh token 吊销和黑名单机制。

如果老师继续问：

> 如果要改成双 token，你会怎么设计？

可以回答：

> 我会让登录接口同时返回 access token 和 refresh token。access token 有效期较短，例如 30 分钟，用于访问普通业务接口；refresh token 有效期较长，例如 7 天或 30 天，用于换取新的 access token。refresh token 可以存入 Redis，key 可以设计为 `refresh:token:{userId}:{tokenId}`，并设置过期时间。当前端发现 access token 过期后，调用刷新接口，后端校验 refresh token 是否存在、是否过期、是否被吊销，校验通过后重新签发 access token。用户退出登录时删除 Redis 中的 refresh token。

## 七、Redis 的使用位置和作用

### 7.1 Redis 当前用途

当前项目中 Redis 主要用于 **邮箱验证码缓存**。

关键位置：

- `backEnd/src/main/java/com/example/backend/service/impl/EmailCodeServiceImpl.java`

使用对象：

- `StringRedisTemplate`

### 7.2 Redis key 设计

项目中主要有两类验证码 key：

| 场景 | key 前缀 | 完整形式 |
|---|---|---|
| 找回密码验证码 | `reset:email:` | `reset:email:{email}` |
| 邮箱登录验证码 | `login:email:` | `login:email:{email}` |

验证码有效期：

```text
600 秒，即 10 分钟
```

### 7.3 为什么验证码适合放 Redis

验证码适合放 Redis 的原因：

1. 验证码是短期数据，不适合长期存在 MySQL。
2. Redis 支持 key 自动过期，天然适合验证码有效期控制。
3. Redis 读写速度快，适合高频校验场景。
4. 校验成功后可以立即删除，实现验证码一次性使用。
5. 不需要额外定时任务清理过期验证码。

### 7.4 当前 Redis 没有做什么

当前项目没有发现 Redis 用于：

- JWT 黑名单
- refresh token 存储
- 用户 Session
- 商品列表缓存
- 热门商品缓存
- 分布式锁
- 接口限流

答辩时可以说：

> 当前 Redis 的落地场景主要是验证码缓存。后续可以继续扩展到接口限流、热门商品缓存、token 黑名单和 refresh token 管理等场景。

## 八、邮箱验证码实现

### 8.1 邮箱验证码流程

邮箱验证码主要用于两个场景：

1. 找回密码。
2. 邮箱验证码登录。

发送验证码流程：

1. 用户输入邮箱。
2. 前端请求后端发送验证码接口。
3. 后端生成 6 位数字验证码。
4. 后端使用 JavaMailSender 发送邮件。
5. 后端将验证码写入 Redis。
6. Redis 设置 10 分钟过期时间。
7. 用户输入验证码后提交。
8. 后端从 Redis 取出验证码并比对。
9. 比对成功后删除 Redis key。
10. 完成登录或重置密码。

### 8.2 关键类和方法

关键位置：

- `backEnd/src/main/java/com/example/backend/service/impl/EmailCodeServiceImpl.java`
- `backEnd/src/main/java/com/example/backend/config/MailConfig.java`
- `backEnd/src/main/java/com/example/backend/controller/AuthController.java`

核心方法：

- `sendCode(String email)`
- `sendLoginCode(String email)`
- `verifyAndRemove(String email, String code)`
- `verifyLoginCodeAndRemove(String email, String code)`
- `sendResetCode(SendResetCodeDTO dto)`
- `resetPassword(ResetPasswordDTO dto)`
- `emailLogin(EmailLoginDTO dto)`

### 8.3 验证码安全设计

当前已经实现：

1. 6 位数字验证码。
2. Redis 10 分钟自动过期。
3. 校验成功后删除验证码。
4. 找回密码时会检查邮箱是否已注册。
5. 密码重置后使用 BCrypt 加密保存。

当前不足：

1. 后端没有严格的邮箱发送频率限制。
2. 后端没有 IP 级别限流。
3. 没有图形验证码或滑块验证码。
4. 前端 60 秒倒计时只能改善用户体验，不能真正防刷。

答辩时可以这样说：

> 邮箱验证码使用 Redis 保存，设置 10 分钟过期时间，校验成功后立即删除，保证验证码具有时效性和一次性。当前项目在前端做了 60 秒倒计时，但后端限流还可以进一步加强，例如使用 Redis 对同一邮箱和同一 IP 做发送频率限制。

## 九、管理员登录与权限设计

### 9.1 管理员登录方式

管理员登录不是单独输入后台账号密码，而是基于微信用户身份进行二次判断。

流程：

1. 用户先完成普通微信登录。
2. 前端携带普通用户 token 请求管理员登录接口。
3. 后端根据当前用户 ID 查询用户 openid。
4. 后端用 openid 查询管理员表。
5. 如果该 openid 是管理员，则签发管理员 token。
6. 前端保存 `adminToken`，后续访问后台接口时使用管理员 token。

关键位置：

- `backEnd/src/main/java/com/example/backend/controller/admin/AdminAuthController.java`
- `webFront/pages/admin/login/login.js`
- `webFront/utils/request.js`

### 9.2 这样设计的好处

1. 管理员身份与微信 openid 绑定，降低账号密码泄露风险。
2. 普通用户 token 和管理员 token 分离，权限边界更清晰。
3. 后端可以通过 token 中的管理员 ID 判断是否有后台权限。
4. 管理端接口和普通用户接口可以采用不同的请求封装。

答辩时可以这样说：

> 系统把普通用户登录和管理员登录做了区分。普通用户登录后只能访问普通业务接口，如果要进入管理后台，还需要根据当前用户的 openid 去管理员表中校验是否具备管理员身份。校验通过后，后端会单独签发管理员 token，从而实现普通用户权限和管理员权限的隔离。

## 十二、文件上传设计

系统提供统一上传接口，用于处理头像、商品图片、商品视频、聊天图片和聊天视频。

关键位置：

支持类型：

- `goods_image`
- `goods_video`

设计好处：

## 十五、评委常见问题与参考答案

### 15.1 为什么选择微信原生小程序，而不是 uni-app？

参考答案：

> 因为本项目主要面向微信生态，功能场景集中在微信小程序端，所以选择微信原生小程序可以更直接地使用微信提供的登录、缓存、页面生命周期和上传等 API。原生开发减少了跨端框架的额外复杂度，也方便调试微信登录和小程序端能力。uni-app 的优势是跨端，但本项目目前没有同时发布到 App 或 H5 的需求，所以原生小程序更合适。

### 15.2 为什么后端选择 Spring Boot？

参考答案：

> Spring Boot 生态成熟，适合快速搭建后端服务。它集成了 Spring MVC、Spring Security、Redis、Mail、MyBatis-Plus 等常用能力，能够满足本项目登录鉴权、数据库访问、验证码、文件上传和后台管理等需求。同时 Spring Boot 的工程结构清晰，适合毕业设计展示系统分层和业务实现。

### 15.3 为什么使用 MyBatis-Plus？

参考答案：

> MyBatis-Plus 在 MyBatis 基础上封装了常见 CRUD、分页和条件构造器，可以减少重复 SQL 代码，提高开发效率。同时它保留了 MyBatis 的灵活性，复杂查询仍然可以自定义 SQL。对于本项目这种包含用户、商品、订单、聊天、收藏等多张表的业务系统，MyBatis-Plus 能显著降低持久层开发成本。

### 15.4 微信登录中的 code 是什么？

参考答案：

> `code` 是微信小程序调用 `wx.login()` 后获得的一次性临时登录凭证。它不能直接代表用户身份，需要由后端携带 `appid` 和 `secret` 调用微信官方的 `jscode2session` 接口，换取用户的 `openid`。`code` 有时效性，而且只能使用一次，因此相对安全。

### 15.5 openid、unionid、session_key 有什么区别？

参考答案：

> `openid` 是用户在某一个小程序下的唯一标识，本项目主要使用 openid 识别微信用户。`unionid` 是用户在同一个微信开放平台主体下多个应用之间的统一标识，适合多个小程序、公众号、App 打通用户身份。`session_key` 是微信返回的会话密钥，主要用于解密微信侧的加密数据，本项目登录身份识别主要依赖 openid，没有重点使用 session_key。

### 15.6 为什么使用 JWT，而不是 Session？

参考答案：

> JWT 更适合前后端分离和小程序场景。传统 Session 需要服务端保存登录状态，并依赖 Cookie 维持会话；而小程序更适合在请求头中携带 token。JWT 本身包含用户身份和过期时间，服务端只需要校验签名即可识别用户，减少了服务端 Session 存储压力，也更方便后期多实例部署。

### 15.7 JWT 里保存了哪些信息？

参考答案：

> 普通用户 token 中主要保存用户 ID、openid、签发时间和过期时间；管理员 token 中主要保存管理员 ID、身份标识、签发时间和过期时间。敏感信息比如密码不会放入 JWT 中，因为 JWT 可以被前端持有和解析，所以只存放必要的身份标识信息。

### 15.8 token 过期后怎么办？

参考答案：

> 当前项目中 token 过期后，后端会校验失败并返回未认证状态。前端统一请求封装会捕获 401 或 403 状态，然后清理本地保存的 token 和用户信息，并提示用户重新登录。管理员 token 失效时也会清理 adminToken 并跳转到管理员登录页。

### 15.9 你的系统有没有实现 refresh token？

参考答案：

> 当前系统没有实现 refresh token，采用的是单 JWT token 方案。这样设计主要是为了降低毕业设计项目的复杂度，同时满足基本登录鉴权需求。后续如果进一步上线，可以扩展为 access token + refresh token 双 token 机制，用短期 access token 访问接口，用长期 refresh token 刷新登录状态，并将 refresh token 存入 Redis 以支持吊销和过期管理。

### 15.10 如果要实现双 token，你会怎么做？

参考答案：

> 登录成功后，后端同时返回 access token 和 refresh token。access token 设置较短有效期，例如 30 分钟；refresh token 设置较长有效期，例如 7 天。refresh token 存入 Redis，并绑定用户 ID、设备信息和过期时间。当前端发现 access token 过期后，调用刷新接口，后端校验 refresh token 是否存在、是否过期、是否被吊销，如果校验通过，则签发新的 access token。用户退出登录时删除 Redis 中的 refresh token。

### 15.11 Redis 在你的项目中用在哪里？

参考答案：

> 当前 Redis 主要用于邮箱验证码缓存，包括找回密码验证码和邮箱登录验证码。验证码 key 按邮箱区分，例如 `reset:email:{email}` 和 `login:email:{email}`，有效期设置为 10 分钟。Redis 支持自动过期，非常适合验证码这种短生命周期数据。

### 15.12 为什么验证码不直接存在 MySQL？

参考答案：

> 验证码属于临时数据，只在几分钟内有效，没有长期保存价值。如果存在 MySQL，需要额外字段或表，并且还要定时清理过期数据。Redis 支持 key 自动过期，读写速度也更快，验证码校验成功后直接删除即可，因此更适合存放验证码。

### 15.13 邮箱验证码如何保证安全？

参考答案：

> 项目中验证码是 6 位数字，存入 Redis 后设置 10 分钟有效期，校验成功后立即删除，保证验证码只能在有效时间内使用一次。找回密码时还会检查邮箱是否已注册，重置密码时使用 BCrypt 对新密码加密保存。不过当前后端限流还可以加强，后续可以用 Redis 增加同一邮箱和同一 IP 的发送频率限制。

### 15.14 如何防止用户一直刷邮箱验证码接口？

参考答案：

> 当前前端做了 60 秒倒计时，但前端限制不能完全防刷。更完整的方案应该在后端实现限流，比如使用 Redis 记录同一邮箱或同一 IP 的发送次数。可以设计 `email:limit:{email}` 和 `email:ip:{ip}` 这样的 key，设置 60 秒内只能发送一次、一天最多发送若干次，超过限制就拒绝请求。这样才能真正从服务端防止刷接口。

### 15.15 管理员权限和普通用户权限如何区分？

参考答案：

> 系统中普通用户和管理员使用不同 token。普通用户登录后只能访问普通业务接口，如果要进入后台，需要基于当前用户的 openid 去管理员表中校验是否是管理员。校验通过后，后端签发管理员 token。访问后台接口时，前端使用 adminToken，后端解析出管理员 ID 后才允许访问后台功能。

### 15.16 如何防止普通用户越权访问管理员接口？

参考答案：

> 首先，后台接口需要认证，不能匿名访问。其次，管理员接口要求 token 中包含管理员身份信息，而普通用户 token 只能解析出普通用户 ID，不能解析出管理员 ID。后端在过滤器和业务层中区分普通用户和管理员身份，因此普通用户即使登录了，也不能直接访问管理员接口。

### 15.17 密码是如何存储的？

参考答案：

> 密码不会明文存储，而是使用 BCrypt 加密后保存。BCrypt 是一种适合密码存储的哈希算法，它内部带有 salt，并且计算成本较高，可以提高暴力破解成本。用户登录时，系统不是解密密码，而是用 BCrypt 的匹配方法比较用户输入密码和数据库中的哈希值。

### 15.18 为什么发布商品需要学生认证？

参考答案：

> 因为系统定位是校园二手交易平台，发布者身份可信度很重要。如果任何人都可以发布商品，可能会出现校外人员发布虚假商品、广告或诈骗信息的问题。通过学生认证后才能发布商品，可以提高平台的安全性和校园属性。

### 15.19 聊天消息是实时的吗？

参考答案：

> 当前聊天功能主要通过接口查询和页面刷新获取消息，不是严格意义上的 WebSocket 实时通信。这样实现复杂度较低，能够满足毕业设计的基本聊天需求。后续如果要提升实时性，可以引入 WebSocket，让后端主动推送新消息，也可以结合微信订阅消息做提醒。

### 15.20 未读消息是怎么实现的？

参考答案：

> 后端根据聊天消息的接收方和已读状态统计未读数量，前端调用接口获取未读数后，在小程序 tabBar 上显示角标。用户进入聊天页面或读取消息后，前端调用标记已读接口，后端更新消息状态，未读数随之减少。

### 15.21 上传接口如何防止恶意文件？

参考答案：

> 当前上传接口按业务类型区分头像、商品图片、商品视频和聊天文件。更完善的安全方案应该增加文件大小限制、后缀名校验、MIME 类型校验、文件内容检测，并将上传文件重命名，避免用户控制文件路径。如果项目上线，还可以把文件存储迁移到对象存储服务，并配合 CDN 加速。

### 15.22 如果用户量变大，系统瓶颈在哪里？

参考答案：

> 可能的瓶颈包括数据库查询压力、图片和视频文件访问压力、聊天消息查询压力以及热门商品列表访问压力。优化方向包括：给常用查询字段建立索引；商品列表、分类和热门数据使用 Redis 缓存；文件上传迁移到对象存储；聊天消息分页查询；后端服务多实例部署；数据库读写分离等。

### 15.23 如何优化商品列表查询？

参考答案：

> 可以从三个方面优化。第一，在数据库层给分类、状态、发布时间、价格等常用筛选字段建立索引。第二，接口层使用分页查询，避免一次性返回大量数据。第三，对热门分类或首页商品列表使用 Redis 缓存，减少数据库压力。当商品发布、下架或修改时，再更新或删除对应缓存。

### 15.24 如何保证订单状态不乱？

参考答案：

> 订单状态应该设计明确的状态流转规则，比如待确认、交易中、已完成、已取消等。后端在更新订单状态时要校验当前状态是否允许流转到目标状态，不能只依赖前端按钮控制。必要时可以使用事务保证订单状态和相关业务数据的一致性。

### 15.25 项目有哪些不足和改进方向？

参考答案：

> 当前项目主要不足包括：JWT 还是单 token，没有实现 refresh token；邮箱验证码后端限流不够完善；聊天功能不是 WebSocket 实时推送；文件上传还可以加强安全校验；Redis 目前只用于验证码，缓存能力没有充分发挥。后续可以从双 token 鉴权、Redis 限流、WebSocket 聊天、对象存储、商品缓存和日志监控等方面继续优化。
