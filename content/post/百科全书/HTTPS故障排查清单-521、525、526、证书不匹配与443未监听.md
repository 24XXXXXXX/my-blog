网站上 HTTPS 后，很多问题不是“完全不能访问”，而是会以各种具体报错的形式出现。

最常见的就是：

- `521`
- `525`
- `526`
- 证书主机名不匹配
- 服务器只有 `80` 没有 `443`
- `Nginx` 配了证书但没有真正 reload
- 证书和私钥不匹配

这篇文章不讲泛泛原理，只给你一份能直接照着查的排障清单。

<!--more-->

## 一、先用一条主线看问题

接入 `Cloudflare` 后，请永远按这条链路排查：

```text
浏览器 <-> Cloudflare <-> Nginx <-> 后端应用
```

任何 HTTPS 问题，基本都落在下面几类：

1. 浏览器到 `Cloudflare` 这一段失败
2. `Cloudflare` 到源站 `Nginx` 这一段失败
3. `Nginx` 本身没正确加载证书或没监听 `443`
4. 域名、证书主机名、`server_name` 三者不一致
5. 业务层回调、跳转、静态资源地址仍指向旧域名

---

## 二、最先执行的基础检查

正式看报错前，先执行下面几步。

### 2.1 看 DNS 是否已经到位

```bash
dig +short example.com A
dig +short example.com AAAA
```

你要确认：

- 域名已经解析到目标 IP
- 如果用了 `Cloudflare` 代理，返回的可能是 `Cloudflare` 的边缘 IP，这属于正常现象

### 2.2 看源站是否真的监听了 443

```bash
ss -ltnp | grep -E ':80|:443'
```

如果你只看到 `80`，没看到 `443`，那 HTTPS 失败就很正常。

### 2.3 看 Nginx 配置是否已加载

```bash
sudo nginx -t
sudo systemctl reload nginx
```

`nginx.conf` 或站点文件写对了但没 reload，是非常常见的问题。

### 2.4 直接对本机用 Host 头测试

```bash
curl -I http://127.0.0.1 -H 'Host: example.com'
curl -k -I https://127.0.0.1 -H 'Host: example.com'
```

这能帮你区分：

- 是域名解析问题
- 还是源站站点配置问题

---

## 三、Cloudflare 521 是什么

`521 Web Server Is Down` 通常表示：

- `Cloudflare` 连源站失败了
- 或者源站拒绝了连接

在 `Nginx` 场景里，最常见原因是：

1. 源站没开 `443`
2. 防火墙没放行 `443`
3. `Nginx` 没启动或配置没生效
4. `Cloudflare` 回源到错误 IP

### 3.1 521 的高频排查顺序

先查：

```bash
ss -ltnp | grep 443
```

再查：

```bash
sudo systemctl status nginx
```

再查：

```bash
curl -k -I https://127.0.0.1 -H 'Host: example.com'
```

如果本机都握手失败，问题就在源站本身，不在 `Cloudflare`。

---

## 四、Cloudflare 525 是什么

`525 SSL Handshake Failed` 表示：

- `Cloudflare` 到源站的 TLS 握手失败

这通常说明：

- 源站确实有 `443`
- 但 TLS 协商没有成功

常见原因：

1. 证书文件损坏或格式不对
2. 私钥文件错误
3. 证书和私钥不匹配
4. `Nginx` 的 `ssl_certificate` / `ssl_certificate_key` 路径写错
5. `Nginx` 改了配置但没真正 reload

### 4.1 如何检查证书和私钥是否匹配

```bash
openssl x509 -noout -modulus -in /path/to/server.pem | openssl md5
openssl rsa  -noout -modulus -in /path/to/server.key | openssl md5
```

如果两边输出不一样，就说明：

- 证书和私钥不是一对

### 4.2 如何检查 Nginx 是否引用了正确文件

看站点配置里是否真的有：

```nginx
ssl_certificate /path/to/server.pem;
ssl_certificate_key /path/to/server.key;
```

并确认路径真实存在、权限可读。

## 五、Cloudflare 526 是什么

`526 Invalid SSL Certificate` 一般表示：

- `Cloudflare` 到源站虽然连上了 HTTPS
- 但源站证书在严格校验下不被接受

在 `Full (strict)` 下，最常见原因是：

1. 证书主机名不匹配
2. 证书已过期
3. 证书链或签发关系不符合校验要求
4. 你访问的是一个域名，但源站证书覆盖的是另一个域名

### 5.1 主机名不匹配是最常见原因

例如你访问的是：

```text
www.computer-store.jtgkw.cn
```

但源站证书只覆盖：

```text
*.jtgkw.cn
jtgkw.cn
```

那它通常不能匹配 `www.computer-store.jtgkw.cn` 这种更深一层子域名。

### 5.2 如何看证书到底覆盖了谁

```bash
openssl x509 -in /path/to/server.pem -noout -subject -issuer -dates -ext subjectAltName
```

重点看：

- `notBefore`
- `notAfter`
- `X509v3 Subject Alternative Name`

## 六、为什么证书主机名不匹配会失败

HTTPS 不是“服务器上有一张证书就行”，而是：

- 当前访问域名
- 证书里的 SAN 主机名
- `Nginx` 的 `server_name`

这三者必须对齐。

例如：

- 访问域名：`computer-store.jtgkw.cn`
- 证书 SAN：`*.jtgkw.cn`
- `server_name`：`computer-store.jtgkw.cn`

这是对齐的。

但如果变成：

- 访问域名：`www.computer-store.jtgkw.cn`
- 证书 SAN：`*.jtgkw.cn`

那通常就不对齐了。

---

## 七、为什么 443 未监听会直接让 HTTPS 失败

因为 `HTTPS` 默认走的就是 `443`。

如果服务器只监听：

- `80`

没有监听：

- `443`

那会出现：

- HTTP 正常
- HTTPS 失败
- `Cloudflare` 代理场景下常表现为 `521`

### 7.1 一个标准的 HTTPS 站点结构至少应包含

```nginx
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate /path/to/server.pem;
    ssl_certificate_key /path/to/server.key;
}
```

如果只有第一段，没有第二段，那 HTTPS 根本没有落地。

---

## 八、为什么 Nginx 配好了文件，线上还是不生效

最常见有四类原因：

1. 改的是项目里的模板文件，不是线上实际生效文件
2. 改完没执行 `nginx -t` 和 `reload`
3. 站点文件存在多个同名或旧版本，实际挂载的是另一份
4. 符号链接仍指向旧配置

### 8.1 排查建议

先看实际链接指向：

```bash
readlink -f /etc/nginx/sites-enabled/example.com.conf
```

再搜全局引用：

```bash
rg -n "listen 443|ssl_certificate|server_name" /etc/nginx /your/project/path
```

这比只盯着一个配置文件靠谱得多。

---

## 九、为什么业务接口正常，支付回调却还是错的

因为你切换域名后，业务配置未必跟着一起切。

你要一起检查：

- 支付回调 URL
- 登录授权回调 URL
- 第三方 webhook URL
- 物流回调 URL
- 前端环境变量里的站点基地址
- 后端 `.env` 或 `application.yml` 中的旧域名

这类问题不一定体现为 HTTPS 握手错误，但会在切域名后表现成“部分业务失效”。

---

## 十、一个推荐的最短排障顺序

如果你只想最快找出问题，直接按这个顺序查：

1. 查 DNS 是否已切到目标域名
2. 查 `443` 是否在监听
3. 查 `nginx -t` 是否通过
4. 查 `ssl_certificate` 和 `ssl_certificate_key` 是否真实存在
5. 查证书 SAN 是否覆盖访问域名
6. 查 `Cloudflare` 的 `SSL/TLS` 模式是不是 `Full (strict)`
7. 本机 `curl` 带 `Host` 头测试 HTTP 和 HTTPS
8. 检查回调和环境变量里是否残留旧域名

只要你严格按这八步执行，绝大多数问题都能快速收敛。

---

## 十一、结论

遇到 HTTPS 问题时，不要一上来就说“证书坏了”。

你应该先区分：

- 是浏览器到 `Cloudflare` 出问题
- 还是 `Cloudflare` 到源站出问题
- 还是源站 `Nginx` 根本没把 `443` 和证书真正跑起来

`521`、`525`、`526` 看起来都像“HTTPS 不通”，但它们对应的问题层次其实不同。

真正高效的做法是把链路拆开，一层一层验证：

- DNS
- 边缘证书
- 源站证书
- `Nginx` 监听
- 域名匹配
- 回调配置

这样排查，问题通常会很快暴露出来。
